# Decision gate for ADR 1: named-pipe and pid-file-lock probe

**Question:** on native Windows, can a coordinator own its pipe name, can a client tell who the server is, what does a client see when the server is busy or gone, and does a pid-file lock still let readers read the pid? ADR 1 (IPC transport and launch protocol) rests its decisions D2, D3, D4 and D7's attribution on these facts. qex answers them on Unix with a socket path, `SO_PEERCRED` and `flock`.

**Answer from this machine:**
- `FILE_FLAG_FIRST_PIPE_INSTANCE` refuses a name that another process of the same user created first (error 5), and the same call without the flag succeeds, so the flag is what closes the squat (P1a, P1b). At its instance limit, a squatter makes the flagged create fail with 231, not 5 (P1d), so "any create failure means the name is taken" is the safe reading.
- A client learns the server's pid, user and the pipe's owner, and the server learns the client's pid (P2a, P2b, P2d).
- An elevated server's pipe with the default descriptor is owned by Administrators (`S-1-5-32-544`), not by the user. A non-elevated client's read+write open is refused (error 5), but a read-only open succeeds, and through it the client identifies the server. With D7's explicit descriptor (owner the user; full access for the user, SYSTEM and Administrators) the owner is the user, the non-elevated client opens read+write, and it identifies the elevated server as the same user (O1: P2c, P2e).
- No pipe and a killed server look the same to a client: `CreateFileW` fails with 2 and `WaitNamedPipeW` returns at once. A relaunched server's flagged create succeeds even while a client still holds a handle to the dead instance; that client gets 109 on read and 232 on write (P4a, P4e, P4f).
- A lock on a byte past the end of the pid file leaves the content readable by another process, in production's order (lock, then truncate and write through the same handle); a lock over the content blocks reads with 33. A second lock attempt fails at once, and the lock goes when the holder is killed (P6a-P6d).

Every row below comes from the committed logs: three full non-elevated runs and the owner's elevated runs (O1).

**Provenance:** every log header records its commit with the probe source matching it ("probe source tree clean vs commit: yes"): commit `35e2bf1` (blob `36084ee`) for the three runs and O1 (i)-(iii), and commit `b74723a` (blob `5adcfbb`) for the two later (ii) pairings. Between the two commits only the pair roles changed (`pair-server --sd d7`, and the client's read-only retry); the checks of the full run did not. The three non-elevated runs give the same id and status on every line, and the same `got=` values once pids and timings are set aside.

## Setup
- Probe: [experiments/named-pipe-probe/](../../experiments/named-pipe-probe/). It's a standalone Rust program using `windows-sys` 0.61.2 and is **not part of qex**. It spawns itself in child roles (squatter, server, client, holder, reader, deleter), so every fact is between real processes; each child takes one Win32 step per line on stdin and answers with the raw result.
- Environment: Windows 11 Home 10.0.26200.9711, rustc 1.98.1 (MSVC). The session's runs are not elevated (TokenElevation 0, integrity `S-1-16-8192`).
- Every pipe create passes one parameter set (`PIPE_ACCESS_DUPLEX`, byte mode, `PIPE_WAIT`, 4096-byte buffers, default timeout) and the same instance limit as its control, so an error 5 comes from the flag and not from a parameter mismatch. Pipe names are unique per run (`lrc-probe-<pid>-<tick>-<check>`).
- SIDs are printed with the machine part masked (`S-1-5-21-X-X-X-<RID>`).
- Run it with: `cargo build --release --locked --manifest-path experiments/named-pipe-probe/Cargo.toml`, then `experiments/named-pipe-probe/target/release/named-pipe-probe.exe --out <file>`.

## What the rows mean for ADR 1
- **D2 (name ownership):** the flag refuses a same-user squatter (P1a), and the control (P1b) shows the refusal comes from the flag. A squatter at its instance limit gives 231 instead (P1d), and a client can hold the name of a dead server open (P4f), so the coordinator reads every create failure as "name taken, refuse". The cross-user squatter (P1c) is not evaluated.
- **D2 and D7 (who the server is):** a same-user client gets the server's pid, user SID and the pipe owner through its own handle (P2a, P2b). The owner is the creator token's TokenOwner: the user when not elevated, Administrators when elevated with the default descriptor (P2c). An elevated coordinator therefore needs the explicit descriptor (owner = user): with it the owner check means "the user" and a non-elevated CLI connects read+write and sees the same user (P2e, `-d7-`); with the default descriptor a non-elevated CLI gets read only, and the Everyone read entry stays (P2e, `-ro-`). An elevated client can identify a non-elevated server (P2f).
- **D7 (attribution):** `GetNamedPipeClientProcessId` gives the client's pid on the server side, elevated or not (P2d, P2f).
- **D4 (liveness):** no pipe and a killed server both give 2 from `CreateFileW` and an immediate return from `WaitNamedPipeW` (P4a, P4e); all instances busy gives 231, then 121 after the timeout (P4b); the window between a client's close and the server's next instance gives 231 (P4c). A client that connects before `ConnectNamedPipe` gets served, and the server sees 535 (P4d).
- **D3 (pid-file lock):** `LockFileEx` on the byte range at `0xFFFFFFFFFFFFFFF0` works with the truncate and write that `hold_pid_file` does (src/paths.rs:532-564), and other processes still read the pid (P6a); locking the content instead would break readers (P6b). P6e shows what replaces the `st_nlink == 0` test (src/paths.rs:554): with `FILE_SHARE_DELETE`, a delete under the lock succeeds, the holder's handle then reports `DeletePending` 1 and `NumberOfLinks` 0, and `CREATE_NEW` on the same name succeeds at once; without `FILE_SHARE_DELETE` the delete fails with 32 and `CREATE_NEW` fails with 80 (ERROR_FILE_EXISTS).
